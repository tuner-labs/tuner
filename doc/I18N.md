# Internationalization

**Tuner** uses [Gnome *i18n*](https://developer.gnome.org/documentation/guidelines/localization.html) for internationalization. This system and library specifies source files (*POTFILES*) from which to extract identified strings for translation (the *.pot* file) and the target languages (*LINGUAS*). During the build process translated strings (*.po* files) are package and the included library uses the appropriate translated strings are then used by the host system when running **Tuner**.

Translations are created, managed and applied via [Weblate](https://hosted.weblate.org/projects/tuner/) as several different components:

* [Glossary](https://hosted.weblate.org/projects/tuner/glossary/) which has common terminology, terms used throughout
* [Application](https://hosted.weblate.org/projects/tuner/tuner-ui/) which covers translatable items in the application UI
* [Countries Languages](https://hosted.weblate.org/projects/tuner/country-names/) static translations of Country and language names
* [Flatpak Metadata](https://hosted.weblate.org/projects/tuner/tuner-desktop/) for packaging and deployment

As languages and translations are updated in Weblate, Weblate generates the appropriate Gnome *.po*  translations files and opens pull requests on **Tuner**.

## Managing Languages and Translations

[![Translation status](https://hosted.weblate.org/widget/tuner/multi-auto.svg)](https://hosted.weblate.org/engage/tuner/)

Anyone can view the current [Tuner](https://hosted.weblate.org/projects/tuner/) translations and add or correct them. Weblate is configured to open *Github Pull Requests* against the *Development* branch of *Tuner*. The *Github* Repo admin can choose to merger the *Weblate* pull request into the repo.

*Weblate* manages the translations by hooks on the *Development* branch watching the *po/\*/\*.pot* files. The *.pot* and *LINGUAS* files drives *Weblate* to produce in its own Repo the *.po* files which contain the translations. *Weblate* opens the *Pull* requests at the admins request.

Components can be *locked* so that more static translations, Countries and Languages for example, can become static.

## i18n in the code

Strings in the UI source code that are candidates for translation are identified using the standard Gnome *xgettext* identification by being encapsulated by *\_()*

Build files to create the translation instructions (*.pot* files), translations (*.po* files) and resulting files themselves exist in the *po* directory. These files do not need to be generated very frequently - only after source strings have changed, or new translations created, and prior to packaging the app.  

Weblate picks up source string changes from the Tuner *development* branch *.pot* files. New translations (*.po* files) arrive in the directories via *pull requests* from Weblate to the Tuner repo development branch.

The *.pot* files are build by *xgettext* scanning the files specified in *POTFILES*. To regenerate the *.pot* files requires a build:

```bash
rm -r build/meson
meson setup --buildtype=debug build/meson -Dtranslation=update
meson compile -C build/meson application-pot
meson compile -C build/meson countries-pot
meson compile -C build/meson extra-pot
```

This:

* Removes the current build directory
* Regenerates the build directory with the flag set to update the translations
* Builds the **main** *.pot* file that relates to the UI
* Builds the **extra** *.pot* file that relates to the Desktop metadata

Updates to the *.pot*, *LINGUAS* and *POTFILES* files *pushed* to the development branch will be picked up by Weblate and can be worked on the Weblate **Tuner** page. Weblate then generates the *.po* translation files and opens a github pull request to have them included in **Tuner**

## Merging Weblate Translations

Occasionally, `.po` files in a Weblate pull request conflict with those in the `development` branch. Since Weblate is the authoritative source for translation files, these conflicts can be resolved automatically using the custom `theirs` merge driver referenced by `.gitattributes`.

From a local clone of the Tuner repository, replace `999` with the pull request number and run:

```bash
git config merge.theirs.name "Always take the incoming branch's version"
git config merge.theirs.driver "cp -f %B %A"

git checkout development
git pull

git fetch origin pull/999/head:pr-999
git merge pr-999

git push origin development
```

The merge driver causes Git to replace any conflicting `.po` files with the versions from the Weblate pull request. Non-translation files are merged normally.

> **Note:** The custom merge driver is stored in your clone and is not part of the repository. It needs to be configured once in each new clone and can be verified with 'git config --local --get merge.theirs.driver'
