# Tuner Release Process

## Local Build

Building Tuner locally is described in the [development doc](DEVELOP.md).

## Flathub

The flathub packaging for **Tuner** is maintained in its own github repo:
<https://github.com/tuner-labs/tuner-flathub> on branch *io.github.tuner_labs.tuner*

### Desktop Menu

The built desktop file must be validated using this command:

```bash
desktop-file-validate build/meson/data/io.github.tuner_labs.tuner.desktop
```

### Version number

The version number is set in one place: `version:` in the `project()` call at the top of `meson.build`. The build
passes it to the app (`VERSION` in `src/Config.vala.in`, shown in the About dialog) and to the metainfo.

The metainfo source is the template `data/io.github.tuner_labs.tuner.metainfo.xml.in`. Exactly one `<release>`
entry, the newest, has `version="@VERSION@"`. At build time `data/meson.build` replaces `@VERSION@` with the
version from `meson.build` and writes `build/meson/data/io.github.tuner_labs.tuner.metainfo.xml`, which is the file
that gets installed. All older entries carry their version written out in full.

#### Moving to a new version

Example: the current release is `2.2.0-beta.2` and the next one is `2.2.0-beta.3`.

**Step 1.** In `data/io.github.tuner_labs.tuner.metainfo.xml.in`, find the entry with `version="@VERSION@"` and
replace `@VERSION@` with the version currently in `meson.build` (the release that entry describes). Leave its date
and notes alone.

Before:

```xml
<release version="@VERSION@" date="@VERSION_DATE@">
```

After:

```xml
<release version="2.2.0-beta.2" date="2026-07-10">
```

**Step 2.** Directly above that entry, inside `<releases>`, add the entry for the new version. Its version is
`@VERSION@`, its date is the planned release date in `YYYY-MM-DD` form, and its notes describe the new release.

```xml
<release version="@VERSION@" date="@VERSION_DATE@">
  <description>
    <p>Feature release:</p>
    <ul>
      <li>...</li>
    </ul>
  </description>
</release>

<release version="2.2.0-beta.2" date="2026-07-10">
```

**Step 3.** In `meson.build`, set the new version in the `project()` call:

```meson
version: '2.2.0-beta.3',
```

**Step 4.** Rebuild and check the result:

```bash
meson compile -C build/meson
grep -m1 '<release ' build/meson/data/io.github.tuner_labs.tuner.metainfo.xml
#   <release version="2.2.0-beta.3" date="2026-11-15">
```

The first `<release>` line must show the new version and date, and the template must contain `@VERSION@` exactly
once. If the release date moves before release day, change the date in the `@VERSION@` entry; nothing else changes.

## Flatpak

Releasing *Tuner* comprises cutting a release of the code in [tuner github](https://github.com/tuner-app/tuner) and then updating the [flathub tuner repo](https://github.com/flathub/io.github.tuner_labs.tuner) which will automatically have the flatpak generated and rolled to Flathub for distribution.

## Flathub Builds

**flathub** builds can be monitored at <https://flathub.org/en/builds>

### Beta Releases

Beta releases should be tagged from [tuner github](https://github.com/tuner-labs/tuner/releases/new) using the Tuner *development* branch - the version in `meson.build` should match the tag - the beta format is *v2\*.\*-beta.\**

Once a beta release has been tagged, the [Flathub *beta* branch](https://github.com/flathub/io.github.tuner_labs.tuner/tree/beta) can be updated via a pull request with the *beta* tag going into the manifest *.json*, and any patches and documentation updated as needed. The pull request will trigger a flathub build, but will not merge the pull request - pull requests should be merged only if they result in a successful build.

Once the beta is successfully built by flathub it will be available for installation and testing for the user community off of the flathub beta repo.

Once a beta roll is deemed a success its pull request can be merged, and a production release can be rolled.

### Production Releases

Production releases are generated from *development* pull requests into *main*. The updated *main* branch should be tagged with a version number format of *v2.\*.\**

Once a release has been tagged, the [flathub repo](https://github.com/flathub/io.github.tuner_labs.tuner) *main* branch can be updated with the *release* tag going into the manifest *.json*, and any libraries, patches and documentation updated as needed. Updates from the *main* branch should be copied in from a direct *pull request* of the *main* branch. The *main* branch **should not** come from a merge *beta* branch to avoid triggering subsequent builds in *beta*.

Once the main production release is built by flathub it will be available for installation and automatically distributed to user community.

The flathub build manifest can be found here:
<https://github.com/louis77/flathub/tree/io.github.tuner_labs.tuner>
